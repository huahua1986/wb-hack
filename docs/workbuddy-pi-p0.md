# 金融buddy 0.4.9：设置与文件工作流 P0

本轮基于 WorkBuddy 5.9.2 / Pi 1.4.0，沿用原版界面资源、金色图标、官方登录与模型桥、文档解析和原有自动/手动执行设置。原版 `/Applications/WorkBuddy.app` 不修改。当前原版安装已自行更新为5.9.3；本轮候选仍明确基于固定哈希的5.9.2源，不混用新版本合同。本说明对应[能力差距分析](workbuddy-cli-pi-capability-gap.md)中的两项P0，不包含完整业务连接器、计划/问答或多Agent建设。

## 推理和上下文压缩

原生推理选择现在进入Host持久设置、Pi运行设置和实际模型请求。档位以官方目录声明的能力为准：`enabled`选择模型默认值，`disabled`仅在模型允许时映射`off`，具名档位必须在该模型的可选范围内。当前目录中的Hy4为固定`high`且不允许关闭，不能静默降为其他档位。设置按会话和模型保存，切换模型后使用该模型此前选择或真实默认。

原生压缩百分比的语义：

| 输入 | 实际行为 |
| --- | --- |
| 空值 / 空字符串 | 使用本版默认80%阈值 |
| 1到100之间的百分比 | 按当前上下文档位计算Pi `reserveTokens`，真实阈值为`contextTokens > contextWindow - reserveTokens` |
| `0` | 关闭预消息阈值压缩；保留手动压缩和真正overflow后的摘要/重试 |

`0`的实现没有关闭Pi的整体自动压缩开关。它设置`reserveTokens=0`，受控扩展仅取消`reason='threshold'`的压缩，放行`manual/overflow`。这避免将原生Max模式误变成“上下文溢出也不恢复”。百分比不是额外的模型输出预算。

设置位于私有的`pi/state/runtimes/<threadId>/`，不改共享`agent/settings.json`，也不把账号认证复制给Pi。启动扩展核对Pi实际合并后的设置与推理状态，通过READY通知后Host才发送本轮。如果项目`.pi/settings.json`覆盖并冲突，会明确拒绝，不能把界面保存当作已经生效。配置变更与模型变更、发送、压缩和回退互斥；运行中不改变预算。

手动压缩可在原生输入框输入`/compact`或`/总结`；原生`command://compact`内容块也会走同一压缩路径，不作为普通用户消息发给模型，不新增聊天轮次、不重放工具。`/compact extra`仍是普通文本。压缩使用当前模型，会消耗相应模型额度；支持停止，失败保留原会话。

当前用量统计仍以Pi报告为准。压缩结果里的`estimatedTokensAfter`是估算；压缩后尚无新回复时，Pi可能暂不给新的用量基准，不能继续使用压缩前累计量冒充当前上下文。

## 文件产物、变更与Diff

原生资源页现在从真实文件记录读取：

- 产物卡与文件树：指向实际生成/修改的本地文件，保留文件名、类型和路径。
- 变更列表：区分创建、修改和删除，按任务与轮次归属。
- 文本Diff：由真实前后快照生成unified hunks，并按原生懒加载合同返回完整变更组。
- PDF、Office等二进制产物：提供文件与快照元数据，可打开产物；不将二进制伪装成文本Diff。

0.4.8实机进一步发现：变更列表虽为`+1/-1`，详情却显示整份当前文件为新增。原样消费者证实，最新manifest没有自己的patch时，`preferConversationChangeArtifact`会继承上轮创建文件的patch；旧patch对当前正文逆向应用失败，最终viewer回退成空旧正文与整份新正文。仅核对计数或只测试创建一轮无法发现这个问题。

0.4.9为每个路径最新的小文本变化直接附带真实hunks，保留逐轮manifests，避免依赖某条UI路径恰好触发lazy detail。内联上限为256KiB、64个最新路径、1秒继续读取预算，优先最近更新；单次已开始的原生diff仍受其2秒上限约束。单文件差异本身过大时使用原生“未生成差异预览”页。二进制、快照不可用、无文本差异或全局预算不足的路径，从当前line-Diff的整条历史投影排除，`diffOmissions`保留真实原因，避免借用旧patch；普通产物、文件树、原始journal、逐轮详情、快照及回退记录保留。不会把二进制或全局预算不足伪称为单文件过大。

文件记录在工具获得正授权之前建立：手动模式在用户允许后捕获，自动模式在回复允许前捕获。`write/edit`跟踪明确目标路径；Bash跟踪其工作目录内的有界范围。工具结束后刷新，轮次终态在文件记录完成后发布，原生`artifactUpdate`触发资源重新加载。

不同任务同时修改同一路径时拒绝冲突授权；Bash的工作目录范围与其他任务目标相交时也会拒绝。不同显式文件可以并发。macOS的锁key采用保守Unicode/大小写归一化，真实用户路径不改写。

快照与索引在私有`pi/state/file-journal/`，不进入应用或DMG。默认限制：单文件25MiB、每轮快照128MiB、总快照1GiB；目录扫描最多2048文件、10000项、32层和5秒，忽略`.git`、`node_modules`等缓存/依赖目录。达到限制会记录范围不完整，拒绝假装整轮可回退；不静默截断Diff。

Bash快照是工作目录窗口内观察到的变化，不等于OS沙箱，也不能撤销目录外、网络、数据库和其他外部系统副作用；不能将其他应用在该窗口内的并发写入可靠归因给某条Bash。未知范围保守处理。

## 原生预览与终态修复

0.4.5首轮实机验证了产物卡、原生Markdown打开、Diff、回退确认、恢复文件和Pi/界面历史、回退后续答，以及GLM原生低档选择和实际请求。原生`/compact`产生真实摘要，Pi估算上下文从78,321降至37,829 tokens，仍为两轮、没有工具重放；该数字不是新的性能SLO或精确计费量。

实机另发现两个界面同步缺口：

- 终态必须发布完整info/list事件并同步线程快照，不能只改变timeline状态，否则侧栏可能保留忙碌标记。完成、失败、取消与缓存刷新都有回归。
- 已加载的预览会缓存正文；产物metadata更新及重复点击同路径不会自动重读。0.4.6对`renderer/assets/src-C0qgplVo.js`的`useLoadFileContent`增加文件变化订阅，但实机证实这只覆盖文件树标签，未覆盖产物卡的独立Markdown组件；该版本没有通过预览验收，也未更新本机安装。

0.4.7保留文件树补丁，并补齐产物卡实际使用的Markdown Host、guest和core更新链。文件树只刷新active、rendered、已有非空正文的只读Markdown；产物卡使用新的条件更新操作，要求当前原生编辑器明确为clean，在原生解析完成、同步提交前再次核对正文、编辑版本、保存活动、组件身份和期限。解析发生在独立的原生临时loader；检查失败不替换当前编辑器，不回退到旧的无条件`updateContent`。

事件只绑定已经打开的本地产物，不能直接把事件路径当作读盘参数。产物卡要求事件大小、原生读前/读后probe及返回UTF-8正文都不超过1MiB。原生`readFile`没有硬读取配额，文件在probe后增长仍可能短暂分配更多内存；限制的是接收内容，不能声称硬内存上限。源模式、未知编辑状态或API、其他格式均跳过。私有诊断仅记录事件命中、跳过、刷新计数，不记录路径、正文或凭据。

构建验证只接受固定5.9.2原始成员SHA和唯一锚点，校验补丁后整个成员SHA。五个已审计成员替回原始SHA后，完整1,958成员摘要必须与固定源一致，由此验证其余1,953成员未修改；依赖、字节范围、原/新SHA均进入manifest。运行中的0.4.6副本不原地改写。静态合同和VM通过不代表真实预览已经刷新，仍需新候选实机验证。

0.4.7实机确认产物卡收到了文件变化事件，但原生预览上下文被判定为cloud，诊断为`nonlocal-skipped`，因此仍显示旧正文；该候选没有安装或封装为通过版。上游原样`useConversationArtifactBinding`把非空`currentConversation.runtimeId`视为云沙箱，即使`transport='local'`也会提升为cloud。Pi facade此前把本地会话ID误填到此字段。0.4.8移除本地Pi info中的`runtimeId`，继续使用`info.id`标识会话；不放松预览的严格local检查，也不改变原版真正云会话、项目和`/workspace`的环境判定。

## 安全回退与历史一致性

原生界面没有独立的“只撤销一个文件”入口，已核验的回退入口同时要求文件恢复和会话分支截断。本版据此完成两边协调，成功后返回原生需要的`ok/branchChanged/truncatedFromRequestId/removedRequestIds`，不会只改文件而保留错误的模型历史。

新轮次在发送前保存Pi追加日志的前缀长度和SHA-256检查点。回退时：

1. 验证文件范围和完整快照，核对当前内容与记录的post-state一致；外部改动、别名歧义或不完整范围会拒绝。
2. 停止本会话Pi进程，验证会话前缀，备份当前完整JSONL及Host线程状态；私有事务记录先落盘。
3. 提交文件恢复、原子恢复Pi前缀，再截断Host对应轮次，清理界面旧历史并刷新资源。后续对话读取恢复后的上下文，不重放已执行的工具。

旧版轮次没有上述检查点，因此仍可查看和续聊，但不能假称已有可靠回退。原生UI通常隐藏首个已加载用户轮次的回退入口，实机验收需要至少两轮。

若发生提交中断，保留快照、整历史备份和私有事务坐标，阻断该任务继续执行，不能把部分成功显示成整轮完成。正常退出会取消尚未提交的回退；进入提交后会等待其完成或持久化中断状态。包含业务MCP等外部工具调用的整轮回退会保守拒绝，避免暗示外部副作用已撤销。
